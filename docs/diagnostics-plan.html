Implementation proposal · Turbo + Next

Plugin diagnostics harness

A dedicated receiver and an exhaustive, on-demand game-state probe, shipped in a separate diagnostics build. Production packages exclude the probe, its settings, and its startup hooks.

Architecture

Diagnostics settings → capture job → typed collectors → bounded JSON chunks → independent uploader → receiver → raw dumps + coverage report

The existing race-event queue remains independent. A diagnostics capture works even when the normal webhook endpoint is empty.

1 · Verify API coverage first

  • Inventory Turbo and Next types, readable members, game globals, and supported helper APIs against the installed Openplanet versions and their references.
  • Prototype reflection enumeration and value reads in both games. Use generated, typed AngelScript collectors wherever generic reflection cannot safely read values.
  • Record every inventoried member as captured, unavailable in this game/state, excluded, unsupported, failed, or truncated, with a reason. Track definitions separately from live values.

Scope: exhaustive coverage of accessible, read-only state. Enumerate method signatures where supported; invoke only verified read-only getters. Do not blindly call game methods, scan raw memory, or construct every game type. Some state exists only in particular modes.

Reference access currently returns HTTP 403. Reflection and serialization capabilities must be proven before committing to exact coverage.

2 · Build the diagnostics receiver

  • Add a standalone Bun service under tools/diagnostics-receiver/, with a configurable bind address, port, storage directory, and dedicated bearer token.
  • Provide POST /diagnostics/v1/chunks and a health endpoint. Validate schema version, capture ID, chunk index, declared limits, and content hash before accepting a chunk.
  • Persist chunks atomically; acknowledge only durable writes. Deduplicate identical retries and reject conflicting chunks. Track incomplete captures and finalize only when the manifest and all expected chunks exist.
  • Store raw JSON, capture metadata, coverage summaries, and per-section errors. Supply CLI commands to list captures, inspect them, and compare two captures by object path.
  • Bound request size, total capture size, disk retention, and incomplete-upload lifetime. Include local run instructions and an example endpoint; deployment is a separate step.

3 · Add the complete dump probe

Collect reachable state from the app, menu, playground, map, game mode, scripts, rules, players, local inputs, race timers, checkpoints, laps, scores, vehicles, camera, and exposed UI/editor state. Include Next helper data when available and equivalent Turbo sources.

  • Provide “Capture full dump”, cancel, progress, and last-result controls, plus optional short capture sequences for before/after transitions.
  • Walk reachable objects with stable dump-local IDs and references for cycles; serialize primitives, enums, strings, vectors, arrays, and object references with explicit type information.
  • Yield between bounded batches. Enforce time, depth, object-count, array-length, string-length, and byte budgets; use generous full-dump defaults with visible truncation and configurable limits.
  • Revalidate handles as scenes change. Isolate recoverable collector errors; describe multi-frame captures with start/end times and per-section timestamps rather than claiming one atomic snapshot.
  • Include game/plugin/runtime versions, build identity, active mode, collector version, API inventory hash, limits, coverage counts, and capture completion state.
  • Exclude authentication material and plugin secrets at collection time. Player identifiers and other sensitive game values get an explicit configurable policy documented in the diagnostics UI.

4 · Separate configuration and delivery

Add a Diagnostics settings category with its own endpoint URL, bearer token, capture limits, and upload status. Empty endpoint disables uploads; captures require an explicit action. Never fall back to the normal webhook URL or token.

Use a separate bounded upload queue with timeouts, cancellation, retry backoff, Retry-After support, and stable chunk IDs. Retain a bounded local spool for interrupted uploads, with visible cleanup controls. Avoid logging payloads or credentials.

5 · Keep diagnostics out of production

Build Contents
Production · default Existing race webhooks; no diagnostics source, settings, collectors, or hooks.
Diagnostics · explicit Same webhook plugin plus diagnostics module and guarded integration hooks; visibly identified artifact.

Extend both Bash and PowerShell packaging using staged files and a diagnostics-only preprocessor define, verified against Openplanet metadata. Keep common settings free of diagnostics declarations. Produce distinct artifact names and automatically inspect production archives for accidental diagnostics inclusion.

6 · Define and verify the contract

  • Update openapi.yaml and docs/webhook-contract.md with the separate diagnostics protocol, authentication, manifest/chunk schemas, error semantics, limits, and retry rules. Add receiver, build, and capture documentation.
  • Test valid and malformed uploads, duplicate/conflicting chunks, missing/out-of-order chunks, interrupted writes, auth failures, oversized payloads, retention, and reconstruction.
  • Verify serializers for cycles, nulls, unusual numeric values, unavailable fields, truncation, and scene changes. Exercise timeout, offline, retry, cancellation, and spool recovery.
  • Build both variants through both packaging scripts where runtimes are available; run existing fixture validation and npx prettier -w ..
  • Compile/load in real Turbo and Next runtimes. Capture menus, loading, solo races, supported multiplayer-local modes, respawn, finish, and map transitions. Measure capture frame cost, memory, upload size, and coverage.

Done means: both games deliver reconstructable dumps with honest coverage reports; normal race delivery still works; interrupted captures are identifiable; production archives contain no diagnostics implementation. Runtime checks that require your game installations will be listed explicitly.

Current repository: normal webhook settings only, no receiver service, and one shared package containing the entire src tree. Proposed order: API feasibility → receiver/contract → probe → uploader/UI → packaging → end-to-end verification.

API references: Turbo · Next · Openplanet preprocessor. This is the planning deliverable; implementation has not started.
